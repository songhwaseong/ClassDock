## 0. 목표와 비목표

**목표**

- 열린 `.docx`의 **본문 글자**와 `.pptx`의 **슬라이드 글자**를 찾아 바꾸고, **원본 서식·이미지·스타일을 건드리지 않은 채** 저장한다(폴더로 연 문서는 원본에, 낱개 파일은 사본으로 — §8).
- 기존 **"여러 파일 찾아 바꾸기"**(Ctrl+K → `replaceAcrossFiles`) 창 안에서 텍스트·코드 파일과 **나란히** 처리한다. 새 화면을 만들지 않는다.
- 위험한 두 가지(**머리말·꼬리말 포함**, **변경 이력 문서 허용**)는 **설정에서 켜고 끈다**. 기본값은 둘 다 꺼짐 — 아무것도 만지지 않은 사용자는 가장 안전한 동작을 얻는다(§12).
- 바꾸지 못한 곳은 **개수를 세어 알린다**. 조용히 빠뜨리지 않는다.
- 완전 오프라인(EXE·오프라인 HTML 동일 동작).

**비목표 (정직한 한계)**

- **문단 추가·삭제, 서식 변경, 표 구조 변경은 하지 않는다.** 이건 Phase 2(문단 제자리 편집)의 몫이다.
- **메모(`comments.xml`)와 도형·텍스트 상자 안 글자는 설정과 무관하게 바꾸지 않는다 — 세기만 한다.** 메모는 남이 쓴 글이라 말없이 고치면 안 되고, 도형은 `w:txbxContent`·DrawingML·VML 세 갈래라 문단 구조가 본문과 달라 v1의 되쓰기 규칙이 그대로 통하지 않는다.
- `.doc`(구형 바이너리)·`.hwp`·`.hwpx`·`.xlsx`는 **이 통로에서 다루지 않는다.** 앞 셋은 구조가 완전히 다르고, `.xlsx`는 이미 ExcelJS 편집기가 있다.
- **암호 걸린 docx는 편집하지 않는다.** 여는 건 되지만(`office-decrypt.js`), 저장하면 암호가 풀린 파일이 되어 버린다. 이건 설정으로도 열지 않는다.
- **`이름_바뀜.docx` 같은 이름 바꾼 사본은 만들지 않는다.** 저장 + 되돌리기 한 갈래로 간다(§8).

## 1. 왜 "run 텍스트 패치"인가

### docx의 형상

```
문서.docx (zip)
├─ [Content_Types].xml
├─ word/document.xml        ← 본문. 여기만 바꾼다.
├─ word/styles.xml, numbering.xml, settings.xml, fontTable.xml
├─ word/media/image1.png …
├─ word/header1.xml, footer1.xml, footnotes.xml, endnotes.xml, comments.xml   ← v1: 세기만
└─ docProps/…, _rels/…
```

본문 XML의 최소 단위는 이렇다.

```xml
<w:p w:rsidR="00A1">
  <w:pPr><w:pStyle w:val="제목1"/></w:pPr>
  <w:r><w:rPr><w:b/></w:rPr><w:t>2025학년도</w:t></w:r>
  <w:r><w:t xml:space="preserve"> 1학기 </w:t></w:r>
  <w:r><w:t>계획</w:t></w:r>
</w:p>
```

### 순진한 치환이 실패하는 이유

Word는 한 문장을 **아무 이유 없이** 여러 `<w:r>`로 쪼갠다. 서식 경계뿐 아니라 편집 이력(`rsid`), 맞춤법 검사 마커(`w:proofErr`), 자동 저장 타이밍 때문에도 쪼갠다. 사람이 "2025"라고 친 글자가 파일 안에서는 이렇게 있을 수 있다.

```xml
<w:r><w:t>20</w:t></w:r><w:proofErr w:type="spellStart"/><w:r><w:t>25</w:t></w:r>
```

`<w:t>` 하나씩 보면서 `"2025"`를 찾으면 **아무 데도 걸리지 않는다.** 화면에 분명히 보이는데 안 걸리는 게 이 기능에서 가장 흔한 배신이다.

→ **찾기는 문단 단위로 이어붙인 글자에서, 되쓰기는 run 경계를 보면서.** 이게 이 설계의 한 문장 요약이다.

### 다른 두 길을 버린 이유

| 방식 | 버린 이유 |
|---|---|
| docx-preview가 그린 DOM을 `contenteditable`로 편집 | docx-preview는 DOM ↔ 원본 XML 매핑을 남기지 않는다. 라이브러리를 포크해 노드마다 출처를 심어야 하고, 저장할 때마다 역매핑이 깨진다. |
| HTML/텍스트를 읽어 docx를 새로 생성 | 스타일·이미지·머리말·번호매기기가 전부 날아간다. 찾아 바꾸기는 **99%가 그대로 있어야 하는** 작업이다. |

`.xlsx` 편집이 ExcelJS로 **"편집한 셀만 되돌려 쓰기"**([spreadsheet-viewer.js:2189](../src/js/spreadsheet-viewer.js:2189))를 택한 것과 정확히 같은 판단이다.

## 2. 손대는 바이트를 최소화한다

| zip 엔트리 | v1 처리 |
|---|---|
| `word/document.xml` | 치환된 새 XML로 **교체** |
| `word/header*.xml` · `footer*.xml` · `footnotes.xml` · `endnotes.xml` | 설정이 켜져 있을 때만 **교체**, 아니면 그대로 복사 |
| 그 밖 **모든** 엔트리 | 바이트 그대로 **복사** |

머리말·꼬리말·각주·미주가 설정 하나로 열리는 이유는 **본문과 XML 구조가 같기 때문**이다. 전부 WordprocessingML의 `<w:p>` / `<w:r>` / `<w:t>`라 §3의 코어가 파트 이름만 바꿔 그대로 돈다. 새 파서가 필요 없어서 이 설정은 공수가 거의 들지 않는다(§11).

zip 재작성에는 **zip.js(`vendor/zip-full.min.js`)** 를 쓴다. JSZip이 아니라 zip.js인 이유:

- `docx` 지연 로드 묶음은 docx-preview 때문에 **전역 `JSZip`을 3.x로 갈았다가 2.6.1로 되돌리는** 곡예를 한다([lazy.js:33](../src/js/lazy.js:33)). 저장 경로가 그 전역 교체 타이밍에 얹히면 재현 어려운 버그가 난다.
- zip.js는 전역 충돌이 없고, 이미 HWPX 미리보기·오피스 통합 검색이 `zip` 묶음으로 쓰고 있다([documents.js:2852](../src/js/documents.js:2852)).
- ODF와 달리 docx는 특정 엔트리를 **무압축(STORE)으로 먼저 넣어야 하는 규칙이 없다.** 전부 deflate로 다시 압축해도 Word가 연다.

재압축으로 잃는 것: 엔트리 타임스탬프, extra field. 본문·서식과 무관하다. 이 사실은 §10의 왕복 테스트로 못 박는다.

## 3. 핵심 알고리즘

### 3.1 문단 모델 만들기

```js
/* 문단 XML 한 개 → 검색용 평문 + 되쓰기용 세그먼트 지도.
   segs[i] = { xmlStart, xmlEnd,   // 원본 XML에서 이 조각의 글자 구간(태그 제외)
               start, end,         // 평문 text 안에서의 구간
               locked }            // true = 바꿀 수 없는 자리(tab·br 등)
   반환: { text, segs } */
function officeParagraphModel(paraXml, paraOffset)
```

- `<w:t …>…</w:t>`를 순서대로 훑어 `officeXmlDecodeText`(코어 재사용)로 디코드해 `text`에 잇는다.
- `<w:tab/>`은 `"\t"`, `<w:br/>`·`<w:cr/>`은 `"\n"`을 **잠긴 세그먼트**로 끼워 넣는다. 평문에 자리를 차지해야 `"가\t나"`가 `"가나"`로 잘못 걸리지 않는다.
- `<w:instrText>`(필드 코드)·`<w:delText>`(추적 삭제분)는 애초에 `<w:t>`가 아니라 자연히 빠진다.
- `xmlStart/xmlEnd`는 **document.xml 전체 기준 절대 오프셋**이다(`paraOffset` 가산). 편집을 문서 단위로 한 번에 모아 적용하기 위해서다.

> 알려진 한계: 태그 탐색이 정규식 기반이라 속성값 안에 날 `>`가 들어 있으면 어긋난다. 코어의 `officeXmlTextRuns`가 이미 같은 가정 위에 서 있고, Word가 그런 XML을 쓰지 않아 v1에서 감수한다.

### 3.2 일치 → 편집 계획

```js
/* 문단 모델 + 매처 → 적용할 편집 목록.
   반환: { edits:[{ xmlStart, xmlEnd, text }], count, skipped, before, after } */
function officePlanParagraphEdits(model, matcher, replacement)
```

**배치 규칙 — 치환문은 일치가 시작된 첫 세그먼트에 통째로 넣고, 겹친 나머지 세그먼트에서는 겹친 부분을 지운다.**

```
문단 평문:  [20][25]학년도          ← 세그먼트 2개
"2025" → "2026"
결과:      [2026][  ]학년도         ← 첫 run의 서식(굵게 등)을 따른다
```

이게 Word 자체 찾아 바꾸기와 같은 결과다. 사용자가 기대하는 동작이고, 문단 안 다른 서식은 손대지 않으므로 "제목만 굵게, 본문은 보통"이 그대로 남는다.

**잠긴 세그먼트를 건드리는 일치는 건너뛴다.** 탭·줄바꿈을 넘나드는 일치는 되쓸 안전한 자리가 없다. 건너뛴 개수는 `skipped`로 올려 화면에 "바꿀 수 없는 곳 N"으로 보고한다.

**빈 run은 지우지 않는다.** `<w:t></w:t>`는 유효한 XML이고, run을 지우면 `rPr`·`rsid`가 함께 사라져 "바꾼 적 없는 부분"의 이력까지 바뀐다.

### 3.3 XML로 되쓰기

```js
function officeReplaceEscape(s)      // & < >  치환 + 허용되지 않는 제어문자 제거
function officeApplyEdits(xml, edits)   // 오프셋 내림차순으로 적용 → 앞 오프셋이 밀리지 않는다
```

- **`xml:space="preserve"`**: 되쓴 글자가 공백으로 시작하거나 끝나면 그 `<w:t>`에 속성을 붙인다. 없으면 Word가 공백을 먹어 `"1학기 계획"`이 `"1학기계획"`이 된다. 이미 속성이 있으면 그대로 둔다.
- 치환문에 줄바꿈이 들어오면 `<w:br/>`로 바꾸지 **않는다.** v1은 글자만 다루고, 줄바꿈은 문단 구조 변경(Phase 2)이다. 대신 매처 단계에서 걸러 안내한다.

### 3.4 미리보기와 적용은 같은 함수를 지난다

```js
/* document.xml 문자열 → 치환된 문자열 + 보고서.
   changes[i] = { para, before, after, count }   ← 미리보기 줄(문단 번호 기준) */
function officeReplacePartXml(xml, matcher, replacement)
```

미리보기 개수와 실제 바뀐 개수가 **다른 코드에서 나오면 반드시 어긋난다.** `batch-replace.js`가 줄 단위로 지키는 원칙([batch-replace.js:44](../src/js/batch-replace.js:44))을 문단 단위로 그대로 옮긴다. 미리보기는 결과 문자열을 버릴 뿐 계산 경로는 동일하다.

매처는 **기존 `batchBuildMatcher`를 그대로 쓴다.** 빈 문자열에 일치하는 패턴 차단, 정규식 오류 처리, `$1` 규칙이 이미 검증돼 있다.

## 4. 바꾸지 않는 문서 — 제외 규칙

```js
/* 바꿀 수 없는 이유를 문자열로, 바꿔도 되면 null 을 돌려준다(순수 함수).
   info  = { encrypted, hasTrackedChanges, hasDataBinding, hasDocumentXml, size }
   opts  = { allowTrackedChanges }   ← 설정값 주입. 함수 자체는 설정을 읽지 않는다. */
function officeExclusionReason(info, opts)
```

| 조건 | 판정 방법 | 처리 | 왜 |
|---|---|---|---|
| 열기 암호 | `looksEncryptedOffice(bytes)` ([office-doc-viewers.js:625](../src/js/office-doc-viewers.js:625)) | **항상 제외** | 저장하면 **암호가 풀린 파일**이 된다. 사용자가 알아채기 어렵고 되돌릴 수도 없다. |
| 변경 내용 추적 | `<w:ins ` 또는 `<w:del ` | **설정으로 전환** (기본 제외) | §12 참조 |
| 내용 컨트롤 데이터 바인딩 | `<w:dataBinding` | **항상 제외** | 바꿔도 바인딩 원본이 다시 덮어써서 **바꾼 게 사라진다.** 취향이 아니라 동작하지 않는 것이라 설정으로 열지 않는다. |
| `word/document.xml` 없음 | zip 엔트리 확인 | **항상 제외** | 비표준 구조 |
| 40MB 초과 | `file.size` | **항상 제외** | 전체를 메모리에 올려 재압축한다. 교실 PC 기준 상한. |

설정값은 **함수 밖에서 읽어 인자로 넣는다.** 순수 코어가 `appSettings`를 직접 보면 `node --test`에서 못 돈다. `batch-replace.js`가 `appSettings.officeReplaceTracked`를 읽어 `opts`로 넘기는 한 줄이 유일한 연결점이다.

**제외된 파일은 목록에서 사라지지 않는다.** 회색 줄로 **이유와 함께** 보여준다. 그냥 빠지면 사용자는 "일치가 없구나"로 오해한다. 설정으로 열 수 있는 사유(변경 이력)는 사유 뒤에 `설정▸문서에서 켤 수 있어요`를 덧붙인다.

## 5. 본문 밖 — 설정에 따라 바꾸거나, 세어서 알린다

파트를 세 갈래로 나눈다.

| 갈래 | 파트 | 설정 끔(기본) | 설정 켬 |
|---|---|---|---|
| 본문 | `word/document.xml` | 바꾼다 | 바꾼다 |
| 딸린 글 | `header*.xml` · `footer*.xml` · `footnotes.xml` · `endnotes.xml` | **세기만** | **바꾼다** |
| 손대지 않음 | `comments.xml`(메모) · 도형/텍스트 상자 | 세기만 | 세기만 |

세는 일은 `officeXmlParagraphLines` + `countRegexMatches`(둘 다 코어에 이미 있음)로 끝난다. 바꾸는 일은 §3의 `officeReplacePartXml`을 파트마다 한 번씩 더 돌리는 게 전부다.

결과 문구는 어느 쪽이든 **숫자로 남는다.**

```
설정 끔:  본문 12곳 바꿈 · 머리말·각주 3곳은 바꾸지 않았어요
설정 켬:  본문 12곳 · 머리말 2곳 · 각주 1곳 바꿈 · 메모 1곳은 바꾸지 않았어요
```

`data-convert`의 **손실 리포트**와 같은 태도다. 못 하는 걸 숨기지 않고 숫자로 보여준다.

**미리보기 개수도 설정을 따라 움직인다.** 설정을 켜면 미리보기에 `머리말 1` 같은 줄이 생기고 총 개수가 늘어난다. 미리보기와 결과가 다른 설정을 보고 있으면 그게 곧 사고다 — 설정값은 모달을 열 때 한 번 읽어 그 세션 내내 고정한다(모달이 떠 있는 동안 설정 창을 열 수는 없다).

순수/브라우저를 한 파일 안에서 `if (typeof window !== "undefined" && window.document)`로 가르는 건 `batch-replace.js`가 이미 쓰는 관례다([batch-replace.js:138](../src/js/batch-replace.js:138)). 테스트는 `window`를 주지 않고 `vm.runInNewContext`로 순수부만 올린다 — 이 프로젝트는 jsdom 없이 `node --test`로 돈다.

### 공개 API

```js
// ── 순수 (tests/office-replace.test.js 대상)
officeParagraphModel(paraXml, paraOffset)
officePlanParagraphEdits(model, matcher, replacement)
officeApplyEdits(xml, edits)
officeReplaceEscape(text)
officeReplacePartXml(xml, matcher, replacement)      // 파트 종류를 가리지 않는다
officeExclusionReason(info, opts)                        // opts = { allowTrackedChanges }
officePartRole(path)          // "body" | "attached" | "countOnly" | null
officeTargetParts(paths, opts)                           // opts = { includeAttached }
officeCountOnlyParts(paths, opts)                        // 딸린 글 먼저, 메모 나중
officePartLabel(path)         // "문단" | "머리말" | "꼬리말" | "각주" | "미주" | "메모"
officeDetectFlags(xml)        // { hasTrackedChanges, hasDataBinding }
officeCountMatches(xml, matcher)

// ── 브라우저
MNOfficeReplace.read(file, opts)             // 찾을 말과 무관한 부분을 한 번만 푼다
//   opts = { includeAttached, allowTrackedChanges }        ← 설정에서 읽어 넣는다
//   → { reason } | { bytes, parts, paths, hasTrackedChanges }
//     parts = { "word/document.xml": xml, "word/header1.xml": xml, … }
MNOfficeReplace.compute(source, matcher, replacement, opts)   // 찾을 말이 바뀔 때마다
//   → { count, skipped, changes, replaced, outside }
MNOfficeReplace.preview(file, matcher, replacement, opts)     // read + compute (단일 파일·테스트용)
MNOfficeReplace.build(bytes, newXmlByPath)   // → Uint8Array (지정한 파트만 교체한 새 zip)
```

세 가지가 설정 때문에 이 모양이 됐다.

- **읽기(`read`)와 계산(`compute`)을 나눴다.** 창이 떠 있는 동안 찾을 말이나 머리말 체크를 고칠 때마다 zip을 다시 풀 수는 없다. 텍스트 파일에서 `textCache`가 하는 역할과 같다([batch-replace.js:422](../src/js/batch-replace.js:422)). 나누지 않고 결과만 캐시하면 **"개수만 세는 파트"의 숫자가 첫 검색어에 얼어붙어** §5의 요구사항이 깨진다.
- `build()`가 **파트 하나가 아니라 경로→XML 지도**를 받는다. 머리말까지 켜면 한 번에 여러 파트를 갈아야 하고, 저장은 zip 재작성 **한 번**으로 끝나야 하기 때문이다.
- `reason`(제외 사유)은 `read` 단계에서 정해진다. 찾을 말과 무관하고 `allowTrackedChanges` 하나에만 걸리므로 창이 사는 동안 한 번만 판정하면 된다.

`officePartRole()`을 순수 함수로 뽑아 두면 "어떤 파트를 어떻게 다루는가"라는 §5의 표가 **테스트 가능한 한 곳**에 모인다. 나중에 도형 텍스트를 여는 날 여기 한 줄만 바뀐다.

## 7. batch-replace 통합

### 대상 선정

현재 `batchIsTargetDoc`은 `isTextExtSearchable`로 판정해 `.docx`가 **확장자 때문에 자연히 빠진다**([batch-replace.js:143](../src/js/batch-replace.js:143)). 이 함수는 그대로 두고 옆에 하나를 더 만든다.

```js
function batchIsDocxDoc(doc){          // 순수 — 테스트 대상
  if (!doc || doc.notebookModel || doc.kind === "pdf") return false;
  return /\.docx$/i.test(String(doc.name || ""));
}
```

`batchReplaceTargetDocs()`가 둘을 합쳐 돌려준다. 팔레트 항목의 노출 조건(`batchReplaceTargetDocs().length > 0`)이 자동으로 docx만 열려 있어도 켜진다.

### 미리보기 항목

파일 항목에 `kind`를 달아 렌더에서 갈라 쓴다.

- 줄 번호 자리 → **`문단 12`**, 딸린 글이면 **`머리말 2`·`각주 1`**(`change.part`로 라벨을 정한다)
- 파일 이름 옆 → 뱃지 **`Word 본문`**, 변경 이력을 허용해 들어온 파일이면 **`변경 이력 있음`**
- 제외된 docx → 회색 줄 + 사유(`체크박스 비활성`)

`before`/`after`는 문단 평문이라 기존 `brClip`·`brEsc`가 그대로 통한다. 목록 구조·CSS 클래스는 손대지 않는다.

### 설정값을 읽는 자리는 한 곳

```js
// openBatchReplace() 안, 모달을 만들 때 딱 한 번
const docxOpts = {
  includeAttached:     appSettings.officeReplaceAttached === true,
  allowTrackedChanges: appSettings.officeReplaceTracked === true
};
```

**모달이 사는 동안 이 값은 얼어 있다.** 미리보기를 만든 뒤 설정이 바뀌면 "12곳"을 보고 눌렀는데 15곳이 바뀌는 일이 생긴다. 설정 창은 모달 위에서 열 수 없으니 실제로는 일어나기 어렵지만, 값을 한 번만 읽어 두면 그 가능성 자체가 없어진다.

`includeAttached`는 옵션 줄의 체크박스와도 묶인다 — **설정은 기본값, 체크박스는 이번 실행값**이다(끄고 켠 값은 저장하지 않는다). 대소문자·정규식 체크박스가 이미 그렇게 동작하므로 일관된다. 반대로 `allowTrackedChanges`는 모달에 내놓지 않는다. 이건 자주 바꾸는 범위 설정이 아니라 **안전장치 해제**라, 실수로 누르기 쉬운 자리에 두면 안 된다.

## 8. 저장 · 되돌리기 · 복원

### 저장 — 원본이 원칙, 사본은 알린다

**바뀐 파일은 되도록 원래 그 자리에 저장한다.** 사본을 만들면 "어느 게 진짜인지" 파일이 두 개로 갈라져 교실에서 더 큰 사고가 난다. 안전망은 사본이 아니라 **되돌리기 + 자동 복원 스냅샷**으로 댄다.

다만 **원본을 덮어쓰려면 파일 쓰기 핸들이 있어야 한다.** 폴더로 연 문서는 핸들이 있고(exe 는 `/source-folder-file` 로 원본 폴더에 쓰는 네이티브 핸들을 준다), 낱개 파일로 끌어다 놓은 문서는 절대 경로 자체가 없어 원본을 찾아갈 방법이 없다. 그래서 갈래가 둘이고, **어느 갈래로 저장됐는지 반드시 사용자에게 말한다**(`saveDocument` 가 `mode` 를 돌려주고 `saveResultText` 가 문구를 만든다). 헤더 배지("원본 저장"/"사본 저장")와 같은 말을 쓴다.

### 저장 경로 (순서대로 시도)

1. `doc.fsHandle`이 있으면 `saveViaFileHandle(bytes, doc.name, doc, { existingOnly:true })` ([code-viewer.js:3745](../src/js/code-viewer.js:3745)) → **원본을 덮어쓴다** (`mode:"original"`)
2. exe 로컬 서버가 있으면 `/save-file` + `X-Save-Path` → 서버가 경로를 **자동 저장 폴더(SaveRoot) 기준으로 풀기 때문에 결과는 사본이다** (`mode:"copy"`). 결과 문구에 "사본으로 저장했어요 + 원본을 고치려면 폴더로 여세요"를 붙인다
3. 둘 다 없으면 **건너뛴다**

3번이 텍스트와 다른 점이 중요하다. 텍스트는 저장 위치가 없어도 편집기에 반영해 두면 사용자가 나중에 저장할 수 있지만, **docx는 편집기가 없다.** 화면만 바꿔 두면 "바뀐 줄 알았는데 파일은 그대로"가 된다. 그래서 저장에 실패하면 **아무것도 바꾸지 않는다.**

### 저장 뒤 뒷정리

```js
doc.sourceFile = new File([bytes], doc.name, { type: DOCX_MIME });   // __fsHandle·__fsDirHandle 이식
doc.render = async () => { host.innerHTML = ""; await renderDocx(fresh, host); };
doc.rendered = false;                    // 다음 활성화 때 새로 그린다
contentCacheDrop(doc.id);                // 통합 검색이 옛 본문을 들고 있지 않게
if (보이는 문서) ensureRendered(doc);
```

`doc.render`를 다시 만드는 게 핵심이다. `loadOffice`의 render 클로저는 **처음 연 File을 붙들고 있어서**([viewer-base.js:10](../src/js/viewer-base.js:10)) `sourceFile`만 갈면 재렌더가 옛 내용을 그린다. 텍스트 경로의 `batchReflectInDoc`이 같은 이유로 같은 일을 한다([batch-replace.js:208](../src/js/batch-replace.js:208)).

이어서 `recoverySnapshotFile(doc, blob, DOCX_MIME)` → `rememberWorkspace`로 자동 복원 묶음도 새 바이트로 갱신한다.

### 되돌리기

undo 항목에 **원본 바이트를 통째로** 담아 두고 같은 저장 경로로 되쓴다. 텍스트처럼 문자열 하나가 아니라 파일 전체라 메모리를 본다.

- undo 보관 합계 상한 **200MB**. 넘으면 적용 전에 "되돌리기 없이 진행할까요?"를 `confirmDialog`로 묻는다.
- 되돌리기 토스트 문구·실패 집계는 `batchReplaceUndo`의 것을 그대로 쓴다.

### 무손실 왕복 — 같은 파일 안

`tests/fixtures/`에 작은 docx를 하나 두고(이미지·스타일·표·머리말 포함), 치환 후 zip을 다시 풀어 **바꾸기로 지정한 파트를 뺀 모든 엔트리의 바이트가 동일한지** 비교한다. 이게 "서식을 안 건드린다"는 주장의 유일한 증거다. 설정 끔/켬 두 경우를 각각 돌린다 — **끔일 때 `header1.xml`이 바이트까지 그대로인지**가 기본값의 안전성을 증명한다.

### e2e — `tests/e2e/docx-replace.spec.js`

docx 열기 → 팔레트로 창 열기 → 미리보기 개수 확인 → 적용 → 재렌더된 화면에 바뀐 글자가 보이는지 → 되돌리기로 원래 글자로 돌아오는지. 설정을 켠 뒤 같은 문서에서 **미리보기 개수가 늘어나는지**도 확인한다(설정이 실제로 미리보기까지 흐르는지가 이 기능의 유일한 배선 위험이다).

## 11. 단계와 공수

| 단계 | 내용 | 공수 |
|---|---|---|
| 1a | 순수 코어(§3) + `officePartRole`·`officeTargetParts` + 단위 테스트 | ✅ 완료 |
| 1b | zip 읽기/쓰기 어댑터(여러 파트) + 무손실 왕복 테스트 | ✅ 완료 |
| 1c | `batch-replace` 통합 · 저장 · 되돌리기 | ✅ 완료 |
| 1d | 설정 2개(§12) · 제외 규칙 · 리포트 문구 · 문서 갱신 | ✅ 완료 |

**설계에서 실제 구현이 달라진 곳**

- `preview()` 하나로 두려던 브라우저 API를 `read`/`compute`로 나눴다(§6). 결과만 캐시하면 "개수만 세는 파트"의 숫자가 첫 검색어에 얼어붙는다.
- 무손실 왕복 검증을 e2e가 아니라 **Node 단위 테스트**로 넣었다(`tests/docx-replace-roundtrip.test.js`). zip.js 가 Node 18+ 의 `Blob`만 쓰므로 브라우저 없이 그대로 올라가, docx 를 만들고 → 바꾸고 → 다시 풀어 **바꾼 파트 말고는 바이트가 같은지**를 CI 속도로 확인할 수 있다.
- 머리말·꼬리말 체크박스는 "설정이 켜져 있을 때만 나타남"이 아니라 **Word 문서가 하나라도 열려 있으면 나타나고 설정값으로 시작**한다. 설정이 꺼져 있을 때 켤 방법이 없으면 체크박스를 둘 이유가 없다.
- 되돌리기 용량 상한은 확인 대화상자 대신 **넘는 파일만 되돌리기 없이 저장하고 결과 문구에 적는** 방식으로 했다. 일괄 적용 도중 뜨는 확인창은 이 창의 Esc 처리와 얽힌다.

```html
<label class="settings-check"><input type="checkbox" id="settingOfficeReplaceAttached"><span>머리말·꼬리말·각주도 함께 바꾸기<small>꺼 두면 본문만 바꾸고, 머리말·꼬리말·각주에 걸린 곳은 개수만 알려 줍니다. 메모(검토 의견)와 도형 안 글자는 어느 쪽이든 바꾸지 않습니다.</small></span></label>
<label class="settings-check"><input type="checkbox" id="settingOfficeReplaceTracked"><span>변경 내용 추적이 켜진 문서도 바꾸기<small>이 프로그램이 바꾼 내용은 Word의 변경 이력에 남지 않습니다. 검토 중인 문서라면 꺼 두세요.</small></span></label>
```

### 기본값과 저장

```js
// state.js → DEFAULT_APP_SETTINGS
officeReplaceAttached: false,   // 머리말·꼬리말·각주까지 바꿀지. 기본은 본문만.
officeReplaceTracked:  false,   // 변경 이력이 켜진 문서를 바꿀지. 기본은 건너뛴다.
```

`app.js`의 설정 열기(`byId(...).checked = ...`)와 저장(`saveAppSettings({...})`)에 두 줄씩 더하면 끝이다. 마이그레이션은 필요 없다 — 없는 키는 `{ ...DEFAULT_APP_SETTINGS, ...saved }`가 기본값으로 채운다([state.js:353](../src/js/state.js:353)).

### 왜 둘 다 기본 꺼짐인가

**되돌릴 수 있는 실수와 되돌리기 어려운 실수는 기본값을 다르게 줘야 한다.**

- 머리말·꼬리말은 **본문에서 안 보이는 곳**이다. 켜져 있는 줄 모르고 "2025→2026"을 돌리면 학교 로고 옆 연도나 쪽 번호 서식까지 바뀌고, 사용자는 바뀐 걸 화면에서 보지도 못한다. 반대로 꺼져 있으면 §5의 숫자가 "머리말 3곳은 안 바꿨어요"라고 알려 주므로, **필요한 사람은 알게 되고 모르는 사람은 다치지 않는다.**
- 변경 이력이 켜진 문서에서 우리가 고친 글자는 **Word의 변경 이력에 남지 않는다.** 검토자가 "누가 언제 뭘 고쳤나"를 이력으로 보고 있는데 거기 없는 수정이 섞이는 건, 파일이 깨지는 것보다 나중에 발견되는 나쁜 종류의 사고다.

두 항목 모두 **필요한 사람은 한 번 켜 두면 계속 쓴다.** 그래서 매번 묻는 대화상자가 아니라 설정이 맞는 자리다.

### 설정이 닿는 범위

| 설정 | 미리보기 개수 | 실제 치환 | 결과 문구 | 저장되는 zip |
|---|---|---|---|---|
| `officeReplaceAttached` | 늘어난다 | 파트가 늘어난다 | 파트별로 나뉜다 | 갈아끼우는 엔트리가 늘어난다 |
| `officeReplaceTracked` | 파일이 목록에 나타난다 | — | 뱃지가 붙는다 | — |

**설정을 바꿔도 미리보기와 결과는 언제나 같은 값을 본다**는 게 이 표의 유일한 요구사항이다. §7의 "설정값을 읽는 자리는 한 곳"이 그걸 보장한다.

## 13. Phase 2로 넘기는 것

여기서 만든 `officeParagraphModel`·`officeApplyEdits`가 그대로 Phase 2(문단 제자리 편집)의 바닥이 된다. Phase 2에서 추가로 필요한 건 문단 추가/삭제(`<w:p>` 통째 삽입), 편집 모드 화면, 그리고 그때 처음으로 "화면에 보이는 것과 저장되는 것"의 대응을 사용자에게 설명해야 한다.

## 14. PowerPoint(.pptx) 확장 — 2026-08-07

Word Phase 1 직후에 붙였다. **코어를 한 줄도 고치지 않았다** — 형식별로 다른 건 파트 표뿐이었다.

### 왜 거의 공짜였나

두 형식은 문단·run·글자 태그가 **이름공간만 다르고 구조가 같다.**

```xml
Word          <w:p>  <w:r><w:rPr><w:b/></w:rPr><w:t>2025</w:t></w:r>  </w:p>
PowerPoint    <a:p>  <a:r><a:rPr b="1"/>        <a:t>2025</a:t></a:r>  </a:p>
```

§3의 정규식은 처음부터 이름공간을 가리지 않게 썼기 때문에(`<(?:[A-Za-z_][\w.-]*:)?p …>`) 슬라이드 XML이 그대로 들어온다. 쪼개진 run 을 넘나드는 찾기, 첫 조각 배치, `xml:space`, 무손실 재압축이 전부 재사용된다.

그래서 모듈 이름을 `docx-replace.js` → **`office-replace.js`**(`MNOfficeReplace`)로 바꿨다. pptx가 의존하는 파일이 `docx-*`라는 이름을 달고 있으면 다음 사람이 반드시 헷갈린다.

### 파트 표만 갈라진다

| 갈래 | Word | PowerPoint |
|---|---|---|
| body(언제나) | `word/document.xml` | `ppt/slides/slideN.xml` |
| attached(설정) | `header*`·`footer*`·`footnotes`·`endnotes` | `ppt/notesSlides/notesSlideN.xml`(발표자 노트) |
| countOnly(세기만) | `comments.xml` | `comments/*` · `charts/*` · `diagrams/*` |
| 무시 | 스타일·테마·번호매기기 | **슬라이드 마스터·레이아웃** |

**마스터·레이아웃을 세지도 않는 이유:** 거기 든 "제목을 입력하십시오"는 화면에 보이는 글이 아니라 빈 자리 안내문이다. 세어서 알리면 없는 일치를 있다고 말하는 셈이 된다.

### PowerPoint에서만 필요했던 두 가지

1. **`<a:fld>` 건너뛰기** — 슬라이드 번호·날짜는 자동으로 채워지는 값이라 사람이 바꿀 대상이 아니다. `officeSkipRanges`의 건너뛸 태그에 `fld`를 더했다(Word의 `<w:fldSimple>`은 이름이 달라 걸리지 않는다).
2. **이름표에 문단 번호를 붙이지 않기** — 파트 자체가 번호를 달고 있어 `슬라이드 3`이면 충분하다. `officePartLabel`이 `{ label, numbered }`를 돌려주고, `numbered:false`면 미리보기가 문단 번호를 생략한다. 정렬도 문자열이 아니라 **경로 속 숫자**로 한다(slide2가 slide10보다 먼저).

### 알려진 구멍 — PowerPoint가 설치된 PC

EXE에서 PowerPoint가 깔려 있으면 `.pptx`를 열 때 **PDF로 정확 변환해서 보여준다**([file-loaders.js:75](../src/js/file-loaders.js:75)). 그러면 화면의 문서는 `kind:"pdf"`라 찾아 바꾸기 대상이 아니다.

즉 **이 기능이 닿는 건 "변환 없이 pptxjs 근사 미리보기로 열린 `.pptx`"뿐이다.** 학교 PC에 PowerPoint가 깔려 있는 경우가 많으므로 실제 도달 범위는 Word보다 좁다. README·사용법에 그대로 적어 두었다.

메우려면 PDF 문서에 원본 pptx 참조를 달고, 치환 후 다시 변환해 새로 그려야 한다. PDF 문서의 저장·편집 상태와 얽히므로 별도 과제로 남긴다.

### 설정 이름도 함께 바뀌었다

`docxReplace*` → **`officeReplace*`**. 설정 문구도 "머리말·꼬리말·각주·**발표자 노트**도 함께 바꾸기"로 넓혔다. 아직 배포 전이라 마이그레이션은 두지 않았다.
