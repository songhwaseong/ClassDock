## 0. 목표와 비목표

**목표**

- 열린 `.docx`의 **문단 글자를 직접 고쳐 쓰고**, 문단을 **추가·삭제**한다.
- 손대지 않은 문단·서식·이미지·머리말은 **바이트 그대로** 남는다(Phase 1과 같은 약속).
- 저장은 **원본 우선**(핸들이 없으면 사본 — 어느 쪽인지 결과 문구로 알린다), 되돌리기는 `MNEditHistory`, 복구본은 기존 스냅샷 경로.

**비목표 (정직한 한계)**

- 드래그한 일부 글자 또는 선택 문단 전체의 **글꼴·크기·굵게·기울임·밑줄·취소선·위/아래 첨자·글자색·형광펜**을 바꾸고, 글머리표·번호 및 지원 서식 복사/붙이기를 제공한다. 손대지 않은 run은 보존한다.
- 표 셀 안에서 문단 자체를 더하거나 지우지는 않는다. 대신 선택 셀 기준 행·열 추가/삭제와 정렬·배경·테두리·열 너비·행 높이, 오른쪽 셀과의 가로 병합 및 `gridSpan` 분할을 지원한다. 세로 병합과 중첩 표는 기존 구조를 보존하기 위해 위험한 편집을 제한한다.
- 마지막 구역의 용지 방향·여백과 기본 머리글/바닥글 첫 문단을 편집한다. 여러 구역을 각각 고르거나 필드가 섞인 머리글을 재구성하지 않는다.
- 선택 문단에 PNG/JPG/GIF를 추가하고 첫 그림을 교체·비율 확대/축소한다. 그림 이동·자르기·텍스트 배치는 이번 범위가 아니다.
- `.pptx`는 이번 범위가 아니다. 슬라이드는 문단보다 도형 배치가 본질이라 같은 화면으로 다루면 거짓말이 된다.

## 1. 한 문장 요약

> **Phase 1의 되쓰기 엔진을 그대로 쓰고, 입력만 "찾기 결과"에서 "문단 diff"로 바꾼다.**

Phase 1의 `officePlanParagraphEdits`가 하는 일은 사실 두 단계다.

```
① 정규식으로 바꿀 구간을 찾는다        → [{ start, end, value }, …]
② 그 구간을 run 조각에 배치한다        → XML 편집 목록
```

②는 형식·용도와 무관한 순수 매핑이다. 이걸 `officeApplyRangesToSegments(model, ranges)`로 떼어내면, Phase 2는 ①만 갈아 끼우면 된다.

```
찾아 바꾸기   정규식 일치      →  ranges  ─┐
문단 편집     diffTextEdit    →  ranges  ─┴→  ② 같은 매핑  →  같은 XML 편집
```

`diffTextEdit`은 이미 코어에 있다([core.js:2069](../src/js/core.js:2069)) — 앞뒤 공통부를 빼고 **바뀐 한 구간**만 돌려주므로, 문단 하나를 고쳤을 때 그 자리만 되쓰게 된다. 사용자가 문단 끝에 한 글자를 더해도 앞쪽 run 들은 바이트가 그대로다.

**이 구조를 택한 이유**는 검증 비용이다. 되쓰기 규칙(첫 조각 배치·`xml:space`·이스케이프·잠긴 조각 건너뛰기)은 Phase 1에서 37개 테스트로 굳혔다. 편집용으로 따로 만들면 같은 함정을 다시 밟는다.

## 2. 화면 — 보기 / 편집 두 모드

| 모드 | 화면 | 왜 |
|---|---|---|
| 보기(기본) | docx-preview — 지금 그대로 | 정확한 모양이 필요할 땐 이쪽 |
| 편집(기본) | **미리보기 제자리 편집** | 보이는 그대로 고친다(Phase 3에서 추가) |
| 편집(대비) | 자체 문단 화면 | 화면 ↔ 문서 대응이 깨지는 문서에서만 물러난다 |

### Phase 3 — 미리보기 위에서 바로 고치기

Phase 2는 "docx-preview 는 DOM ↔ XML 매핑을 남기지 않는다"를 이유로 자체 화면을 만들었다. 그 사실 자체는 지금도 맞다 — `parseParagraph(e)`가 원본 XML 요소를 받고도 모델에 참조를 남기지 않고, `renderParagraph`는 `<p>`에 클래스·스타일만 붙인다.

**대신 순서로 잇는다.** 미리보기 DOM에서 본문 문단만 골라내면(`inlineBodyParagraphs`) 그 차례가 `officeParagraphOutline`의 차례와 같아진다. docx-preview 가 본문 밖에서 만드는 `<p>`는 전부 조상으로 갈라지기 때문이다.

| 본문이 아닌 `<p>` | 어디에 생기나 | 어떻게 거르나 |
|---|---|---|
| 머리말·꼬리말 | `<header>`/`<footer>`, **쪽마다 되풀이** | `closest("header, footer")` |
| 각주·미주 | 쪽 아래 `<ol>` | `closest("ol")` |
| 텍스트 상자 | 그림 `<div>` 안에 본문처럼 그린다 → `<p>` 안의 `<p>` | 조상에 `<p>` 가 있으면 뺀다 |

**순서가 맞다는 걸 믿지 않는다.** `mc:AlternateContent`(Choice·Fallback 양쪽에 `<w:p>`가 있다)·`<w:sdt>`·`altChunk`·렌더러가 그리지 못한 요소가 대응을 깰 수 있고, **깨진 채로 저장하면 사용자가 고친 것과 다른 문단이 바뀌면서 화면상으로는 멀쩡해 보인다.** 먼저 문단 글자를 전부 맞춰 보고(`officeInlineMapVerify`), 어긋나면 저장하지 않을 임시 북마크를 각 본문 문단에 넣어 docx-preview가 만든 `<span id>`로 XML 문단 위치를 정확히 다시 찾는다. 화면에도 없는 문단은 억지로 만들지 않으며, 북마크로도 잇지 못한 경우에만 Phase 2 목록 화면으로 물러난다.

대조는 **공백을 다 지운 글자**로 한다. docx-preview 가 `<w:tab/>`을 `&emsp;`(U+2003)로, `<w:br/>`을 `<br>`(textContent 에 아무것도 안 남긴다)로 그려서 평문과 공백 표현이 애초에 다르기 때문이다. 읽을 때는 `inlineTextOf`가 이 둘을 `"\t"`·`"\n"`으로 되돌려 모델 평문과 같은 자리로 맞춘다.

되쓰기는 **Phase 2 엔진을 한 줄도 바꾸지 않는다.** 입력이 목록 행에서 DOM `textContent`로 바뀔 뿐, 행 배열 → `officeParagraphEditPlan` → `officeApplyEdits` 경로는 그대로다.

토글 버튼은 표 편집기의 `표 편집·정렬`과 같은 자리·같은 문구 규칙을 쓴다([spreadsheet-viewer.js:2194](../src/js/spreadsheet-viewer.js:2194)). 사용자가 이미 배운 패턴을 재사용한다.

### 배너는 필수다

편집 화면은 사용자가 **그 화면을 문서라고 착각하기 쉽다.** 표 편집기는 표가 원래 격자라 착시가 적지만, Word 문서는 여백·쪽 나눔·글꼴이 다 다르게 보인다.

```
✎ 편집 화면 — 글자만 고치는 간이 표시예요. 글꼴·여백·쪽 나눔은 실제 문서와 다르게 보입니다.
   손대지 않은 곳의 서식은 저장할 때 그대로 유지됩니다.
```

두 번째 줄이 핵심이다. 첫 줄만 있으면 "그럼 저장하면 서식이 날아가나?"로 읽힌다.

### 문단 하나가 어떻게 보이나

```
┌──────────────────────────────────────────┐
│ 제목1 │ 2025학년도 학급 운영 계획          │  ← 왼쪽: pStyle 이름(읽기 전용)
├──────────────────────────────────────────┤
│       │ 1. 학급 규칙을 함께 정한다          │
└──────────────────────────────────────────┘
```

- 문단 본문은 `contenteditable` 한 칸이며, 문단을 선택하면 run 서식 도구가 나타난다. 글자를 드래그하면 그 범위에만, 선택 범위가 없으면 문단의 모든 텍스트 run에 적용하고 도형 안 글자는 제외한다.
- 왼쪽 스타일 이름(`제목1`·`본문`)은 `<w:pStyle w:val>` 을 그대로 읽어 보여준다. 문단이 무엇인지 알려 주는 최소 정보이고, 새 문단이 어떤 스타일을 물려받는지도 여기서 보인다.
- 표 안 문단 자체의 추가·삭제 버튼은 주지 않는다. 셀을 선택하면 행·열 구조, 셀 서식, 오른쪽 병합·가로 분할 도구가 나타난다.

## 3. 편집 모델

편집 중 상태는 **문단 배열 하나**다.

```js
paragraphs = [{
  index,        // 원본 XML 에서의 문단 순번(되쓰기 대상 찾기용)
  text,         // 화면에 보이는·편집되는 평문
  original,     // 처음 읽은 평문 (diff 기준 — 여러 번 고쳐도 원본 대비로 계산한다)
  style,        // pStyle 이름(표시용)
  inTable,      // 표 안 문단인가(추가·삭제 금지)
  locked,       // 탭·줄바꿈 조각을 품었는가
  added,        // 이번 편집에서 새로 만든 문단인가
  removed       // 지운 문단인가
}]
```

**`original` 을 들고 있는 이유**: diff 를 "직전 상태"가 아니라 **처음 읽은 상태** 대비로 계산해야, 여러 번 고친 뒤에도 편집이 한 구간으로 정리되고 손대지 않은 run 이 최대로 보존된다. 직전 상태와 비교하며 누적하면 편집을 반복할수록 run 이 잘게 부서진다.

### 잠긴 문단

탭·줄바꿈 조각(`<w:tab/>`·`<w:br/>`)을 품은 문단은 평문에 `\t`·`\n` 이 보인다. 그 자리를 건드리는 편집은 되쓸 안전한 자리가 없으므로 **그 문단만 저장에서 제외하고 이유를 화면에 남긴다.** Phase 1의 `skipped` 와 같은 태도다 — 조용히 실패하지 않는다.

## 4. 문단 추가 · 삭제

여기가 Phase 1에 없던 유일한 새 영역이다.

### 추가 — 직전 문단의 `<w:pPr>` 를 복제한다

```js
officeNewParagraphXml(templateParaXml)   // 순수: pPr 만 남기고 run 을 비운 <w:p> 를 만든다
```

Word 에서 Enter 를 치면 **직전 문단의 문단 서식(스타일·정렬·들여쓰기)을 물려받는다.** 같은 규칙을 그대로 쓴다. `<w:pPr>` 를 통째로 복사하고 run 은 비운다.

단, `<w:pPr>` 안의 `<w:sectPr>`(쪽 설정)은 **복제하지 않는다.** 복제하면 쪽 나눔이 하나 더 생긴다.

### 삭제 — `<w:p>…</w:p>` 통째로

```js
officeRemoveParagraphRanges(xml, indexes)   // 순수: 지울 문단의 XML 구간 목록
```

**마지막 `<w:sectPr>` 를 품은 문단은 지울 수 없다.** 문서 끝 문단의 `<w:pPr><w:sectPr>` 에 용지·여백·머리말 연결이 들어 있어, 지우면 쪽 설정이 통째로 날아간다. 화면에서 그 문단의 삭제 버튼을 없애고 이유를 툴팁으로 단다.

표 안 문단 자체는 추가·삭제 금지다. 표 행·열은 아래 별도 구조 편집을 사용한다.

### 표 구조·셀 서식 편집

`officeTableOutline`이 바깥쪽 표의 행·셀 범위와 문단별 `tableIndex/tableRow/tableCell` 좌표를 만들고,
`officeTableStructureEdit`이 한 동작을 절대 오프셋 편집 목록으로 바꾼다. 새 행·셀은 선택 위치의
`trPr`·`tcPr`·첫 문단 `pPr`을 물려받되 글자는 비운다. 열 변경 시 `tblGrid/gridCol`도 함께 바꾼다.

- 행 추가·삭제: 가로 병합은 행별 모양 그대로 보존한다. 세로 병합 표는 병합 범위를 임의로 늘리거나 끊지 않도록 제한한다.
- 열 추가·삭제: 단순 직사각형 표만 허용한다. `gridSpan`·`hMerge`·`vMerge`·`gridBefore/gridAfter`가 있으면 제한한다.
- 중첩 표: 바깥 표와 안쪽 표 좌표를 섞지 않도록 구조 편집을 제한한다.
- 표 구조를 바꾸기 직전의 문단 글자 편집은 먼저 현재 XML에 반영하고, XML 버전 번호를 편집 기록에 넣어 Ctrl+Z/Ctrl+Y로 표 구조까지 되돌린다.
- `officeTableCellFormat`이 선택 셀의 현재 가로·세로 정렬, 배경색, 테두리색, 열 너비, 행 높이를 읽는다.
- `officeTableFormatEdit`은 셀의 모든 문단 정렬, `tcPr`의 배경·네 면 테두리·세로 정렬, 열 전체 `tcW`와 `tblGrid`, 선택 행 `trHeight`를 함께 갱신한다.
- 중첩 표에서는 셀 서식을 제한하고, 병합 또는 비직사각형 표에서는 열 너비 변경만 제한한다. 행 높이와 단순 셀 서식은 안전한 범위에서 유지한다.
- `officeTableCellMergeEdit`은 같은 행의 오른쪽 셀 본문을 보존한 채 `gridSpan`으로 합치며, 분할은 span 수만큼 빈 셀을 되살린다. 세로 병합은 거부한다.

### 문단 글자 서식

`officeParagraphTextFormat`이 선택 위치 run의 직접 글꼴·크기·굵게·기울임·밑줄·취소선·위/아래 첨자·글자색·형광펜을 읽는다. `officeParagraphFormatEdit`은 범위가 있으면 걸친 run을 앞·선택·뒤로 안전하게 나누고 선택 조각만, 범위가 없으면 문단의 모든 텍스트 run을 편집한다. 글꼴은 `ascii/hAnsi/eastAsia/cs`를 함께 기록하고, 크기는 Word의 반포인트 단위 `sz/szCs`로 저장한다. 굵게·기울임·취소선 해제는 `val="0"`, 밑줄 해제는 `val="none"`을 명시한다. 첨자는 `vertAlign`의 `baseline/superscript/subscript`, 임의 형광펜 색은 run 음영(`rPr/shd`)으로 저장한다. 서식 지우기는 지원 직접 속성만 제거하고 언어·교정·숨김 같은 다른 `rPr` 자식은 보존한다.

### 목록·페이지·머리글·그림

- 목록은 `numbering.xml`에 앱 전용 bullet/decimal 정의를 한 번만 만들고 문단 `numPr`로 연결한다. 관계와 `[Content_Types].xml`도 함께 갱신한다.
- 페이지 설정은 마지막 `sectPr`의 `pgSz/pgMar`만 바꾸며 다른 구역 속성은 보존한다.
- 머리글·바닥글은 기존 관계를 따라 첫 문단 글자만 고치거나, 없으면 새 파트·관계·기본 참조를 만든다.
- 그림은 새 `word/media` 엔트리와 이미지 관계를 만들고 DrawingML inline 요소로 문단에 넣는다. 교체는 공유 파일을 덮지 않고 새 media 경로로 관계 대상을 바꾸며, 크기는 `wp:extent`와 `a:ext`를 함께 조절한다.

### 문단 배치 서식

`officeParagraphLayoutFormat`이 선택 문단의 정렬, 줄 간격, 문단 앞뒤 간격, 좌우·첫 줄·내어쓰기를 읽고 `officeParagraphLayoutEdit`이 `pPr`의 `jc/spacing/ind`만 수정한다. 줄 간격과 앞뒤 간격은 같은 `spacing` 요소를 공유하므로 속성 단위로 갱신해 서로 덮어쓰지 않는다. 들여쓰기도 `left/right/firstLine/hanging`을 독립적으로 보존한다. 문단 배치 지우기는 이 세 직접 속성만 제거하므로 `pStyle`과 `sectPr`의 용지·여백·머리말 연결은 그대로 남는다.

### 편집을 한 번에 적용하는 순서

편집(텍스트 교체)·삭제·추가가 섞이면 오프셋이 엉킨다. 셋 다 **문서 기준 절대 오프셋을 가진 편집 목록**으로 바꾼 뒤, Phase 1의 `officeApplyEdits`(오프셋 내림차순 적용)에 한 번에 넘긴다. 새 함수는 필요 없다.

```
텍스트 편집 → ranges → 조각 매핑 → edits ─┐
문단 삭제   → 문단 구간 → edits          ─┼→ officeApplyEdits(xml, edits)
문단 추가   → 삽입 지점 + 새 XML → edits ─┘
```

## 5. 저장 · 되돌리기 · 복원

전부 이미 있는 것을 쓴다.

| 무엇 | 어디 것 |
|---|---|
| 저장(핸들 → `/save-file`) | Phase 1 `batchOfficeSaveBytes` 와 같은 규칙 — 공용 함수로 뽑는다. 핸들이면 원본, `/save-file` 이면 사본 |
| zip 재작성 | `MNOfficeReplace.build` |
| 되돌리기 | `MNEditHistory.create({ kind:"text" })` — 스냅샷은 문단 배열 |
| 복구본 | `recoverySnapshotFile` + `rememberWorkspace` |
| 재렌더·검색 캐시 | `doc.sourceFile` 교체 + `contentCacheDrop` |

저장 실패 시 **화면도 되돌리지 않는다** — Phase 1과 달리 여기는 편집기가 있으므로, "저장 안 됨" 표시를 남기고 사용자가 다시 시도하게 둔다(`markDocumentDirty`). 텍스트 편집기와 같은 규약이다.

## 8. 단계

| 단계 | 내용 | |
|---|---|---|
| 2a | 순수 코어(§3·§4) + 단위 테스트 · 왕복 테스트 | ✅ |
| 2b | 편집 모드 화면 + 배너(§2) | ✅ |
| 2c | 저장·되돌리기·복원 연동(§5) | ✅ |

**설계에서 실제 구현이 달라진 곳**

- `officeParagraphEditPlan(xml, rows)` 을 하나 더 두어 **화면이 행 배열만 들고 있게** 했다. 설계에는 없던 층인데, 이게 없으면 "어느 문단을 어떤 순서로 되쓸지" 가 DOM 코드에 스며들어 검증할 수 없다.
- **같은 자리에 새 문단이 여럿이면 한 편집으로 합친다.** 오프셋이 같은 삽입을 따로 넣으면 `officeApplyEdits` 의 정렬이 순서를 보장하지 않아 줄이 뒤집힌다(테스트로 굳혔다).
- **저장 뒤 편집 기준을 새 XML 로 다시 잡는다.** 안 그러면 두 번째 저장이 이미 반영된 편집을 옛 문단 위치에 또 적용한다. 이것도 테스트로 남겼다.
- 저장 버튼에 `class="run-save"` 를 달아 **Ctrl+S 를 공짜로 얻었다** — `app.js` 의 `saveCurrent` 가 활성 문서의 `.run-save` 를 눌러 주는 기존 경로다.
- 저장·반영·복원 스냅샷은 `batch-replace` 와 규칙이 같아야 하므로 `MNOfficeReplace.saveDocument`/`reflectSaved`/`rememberSaved` 로 공용화하고, 찾아 바꾸기도 그걸 쓰도록 바꿨다.
